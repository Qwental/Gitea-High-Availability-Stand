# Описание роли: restic_server

Роль предназначена для установки и конфигурации `rest-server` (официального высокопроизводительного HTTP-бэкенда для Restic) в качестве централизованного сервера резервного копирования.

## Требования (Requirements)

* **ОС**: Ubuntu/Debian.
* **Зависимости пакетов**: `apache2-utils` (для генерации `.htpasswd`), `python3-passlib`, `cron`.
* **Сеть**: Открытый порт `8000/TCP` для входящих подключений от агентов (целевых хостов).
* **Доступ**: Выход в интернет для загрузки бинарного файла `rest-server` с GitHub.

## Переменные роли (Role Variables)

Определяются на уровне `group_vars/backup` или `host_vars`.

| Переменная | Описание | Обязательность |
| --- | --- | --- |
| `target_arch` | Архитектура целевой системы (например, `amd64`, `arm64`) для формирования URL загрузки. | Да |
| `restic_rest_user` | Имя пользователя для Basic Authentication. | Да |
| `restic_rest_password` | Пароль пользователя для Basic Auth (должен храниться в Ansible Vault). | Да |
| `restic_repo_password` | Мастер-пароль шифрования репозитория Restic. Необходим локальному скрипту для выполнения `prune` (Vault). | Да |

## Техническая реализация и архитектура (Architecture Notes)

### 1. Изоляция и привилегии (Security Model)

* Создается выделенный системный пользователь и группа `backup`.
* Данные хранятся в директории `/backup/restic` с правами `0700` (владелец: `backup`).
* Демон `rest-server` работает от имени пользователя `backup`, что минимизирует радиус поражения при RCE-уязвимостях (Source: *Standard Linux Security Practices*).

### 2. Защита от Ransomware / Компрометации (Append-Only)

* В systemd-юните `rest-server.service` жестко задан флаг `--append-only`.
* Это гарантирует, что клиенты (агенты на серверах баз данных и приложений) могут только добавлять новые слои данных, но **не могут удалить или изменить** существующие резервные копии.
* *Уязвимость:* Флаг `--tls=false` передает данные и учетные данные Basic Auth в открытом виде. В production-среде (без защищенного VPN/L2-туннеля) это недопустимо. Требуется настройка TLS-сертификатов (или терминация SSL на балансировщике).

### 3. Механизм аутентификации

* Используется встроенная Basic Authentication.
* Учетные данные генерируются с помощью утилиты `htpasswd` с флагом `-B` (использование надежного алгоритма bcrypt). Парольный файл хранится по пути `/backup/restic/.htpasswd`.

### 4. Обслуживание репозитория (Retention & Maintenance)

Для обхода ограничений `--append-only` со стороны клиентов, операция очистки (`prune`) выполняется локально на самом сервере резервного копирования.

* **Скрипт**: Разворачивается шаблон `prune.sh.j2` в `/usr/local/bin/restic-prune.sh`. Скрипт обращается напрямую к файловой системе (`RESTIC_REPOSITORY="/backup/restic"`), минуя REST API.
* **Политика хранения (Retention Policy)**:
* 7 последних ежедневных копий (`--keep-daily 7`).
* 4 еженедельных (`--keep-weekly 4`).
* 6 ежемесячных (`--keep-monthly 6`).


* **Расписание**: Автоматизировано через `cron`. Запускается ежедневно в 04:00 системного времени (`Europe/Moscow`). Логи перенаправляются в `/var/log/restic-prune.log`.
