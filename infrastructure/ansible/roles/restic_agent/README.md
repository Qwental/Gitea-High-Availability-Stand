# Описание роли: restic_agent

Роль предназначена для настройки клиентской части (агента) системы резервного копирования на целевых узлах инфраструктуры. Она обеспечивает автоматизированное создание бэкапов баз данных PostgreSQL и файловой системы хранилища на централизованный `rest-server`.

## Требования (Requirements)

* **ОС**: Ubuntu/Debian.
* **Сетевой доступ**: Доступ к порту `8000/TCP` узла `backup-srv`.
* **Привилегии**: Для бэкапа БД требуются права суперпользователя (или доступ к пользователю `postgres`), для FS — доступ к чтению целевых директорий.

## Переменные роли (Role Variables)

Данные берутся из `group_vars/all/vault.yml` и конфигурации инвентаря.

| Переменная | Описание |
| --- | --- |
| `restic_rest_user` | Пользователь для Basic Auth на rest-server. |
| `restic_rest_password` | Пароль для Basic Auth (Ansible Vault). |
| `restic_repo_password` | Пароль для шифрования репозитория Restic (Ansible Vault). |
| `db_vip` | Виртуальный IP кластера БД. Используется для определения Master-ноды. |
| `storage_vip` | Виртуальный IP кластера хранилища. |

## Техническая реализация (Architecture)

### 1. Интеграция с HA-кластерами (Master-only Backup)

Ключевая особенность роли — проверка наличия VIP-адреса на узле перед запуском бэкапа. Это предотвращает создание дубликатов или бэкапов с неактуальных реплик.

* **Логика скриптов**: Скрипты `backup-pg.sh` и `backup-fs.sh` выполняют команду `ip a | grep -q "{{ VIP }}"`. Если VIP не найден, выполнение завершается успешно с сообщением "Node is not Master. Skipping".

### 2. Типы бэкапов

Роль адаптивна и настраивает компоненты в зависимости от принадлежности хоста к группам Ansible:

* **Группа `db_cluster` (PostgreSQL)**:
* Выполняется логический бэкап через `pg_dumpall`.
* Данные передаются в Restic через `stdin`, что исключает создание временных файлов дампов и экономит место на диске.


* **Группа `storage_cluster` (Shared Storage)**:
* Выполняется бэкап директории `/data/brick1/gv0` (предположительно кирпич GlusterFS или путь экспорта NFS).



### 3. Автоматизация через Systemd

Для обеспечения надежности вместо классического `cron` используются пары **Systemd Service + Timer**:

* **Таймер**: Настроен на запуск каждые 30 минут (`OnCalendar=*:0/30`) с рандомизированной задержкой в 60 секунд (`RandomizedDelaySec=60`) для исключения "громового стада" (Thundering Herd) запросов к бэкап-серверу.
* **Сервис**: Тип `oneshot`. Запускает соответствующий bash-враппер.

### 4. Инициализация репозитория

Роль автоматически инициализирует репозиторий Restic через REST API при первом запуске (`restic init`). Задача выполняется однократно (`run_once: true`), ошибки "уже инициализировано" игнорируются (`failed_when`).

## Файлы конфигурации и скрипты

* **/etc/restic/restic.env**: Содержит переменные окружения (`RESTIC_PASSWORD`, `RESTIC_REPOSITORY`) для аутентификации агента. Права доступа ограничены `0600`.
* **/usr/local/bin/backup-*.sh**: Скрипты-врапперы, содержащие логику проверки ролей и вызова команд `restic`.

## Пример использования (Example Playbook)

Роль обычно включается в общий плейбук развертывания компонентов:

```yaml
- name: Deploy Backup Agents
  hosts: db_cluster:storage_cluster
  become: yes
  roles:
    - role: restic_agent
      tags: backup_agent

```
