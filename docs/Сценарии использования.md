### Сценарий 1: Отказ балансировщика нагрузки (HAProxy / gitea-proxy-01)

**Контекст:** В кластере настроены два узла прокси-сервера (`gitea-proxy-01` и `gitea-proxy-02`), управляемые Keepalived. `gitea-proxy-01` является `MASTER` с приоритетом 110, `gitea-proxy-02` — `BACKUP` с приоритетом 100. На них привязан плавающий IP-адрес `gitea_vip` (`172.20.0.20`), на который поступает весь HTTP-трафик пользователей.

**Событие:** Узел `gitea-proxy-01` внезапно выходит из строя

**Цепочка событий (Failover):**

1. **Keepalived обнаруживает сбой:**
* Если процесс `haproxy` падает, локальный скрипт `vrrp_script` на `gitea-proxy-01` (основанный на `killall -0 haproxy`) возвращает ошибку. Это уменьшает приоритет узла (`weight -20`), делая его 90.
* Если узел падает полностью, `gitea-proxy-02` перестает получать VRRP-анонсы (hello-пакеты) от `MASTER`.


2. **Переключение роли (VRRP Transition):** Узел `gitea-proxy-02` видит, что его приоритет (100) выше текущего приоритета мастера (90 или 0, если тот мертв). Он переходит в состояние `MASTER`.
3. **Миграция VIP:** `gitea-proxy-02` назначает IP-адрес `172.20.0.20` на свой сетевой интерфейс (`eth0`) и рассылает Gratuitous ARP (GARP) запросы в сеть `lab-internal-net`, чтобы обновить кэши коммутаторов и соседних контейнеров.
4. **Возобновление обслуживания:** Весь новый трафик на `172.20.0.20` начинает поступать на `gitea-proxy-02`, который маршрутизирует его на узлы приложения (Gitea). Существующие TCP-соединения будут разорваны, и клиентам потребуется выполнить повторный запрос. Время простоя (Downtime) составляет около 2-4 секунд (время VRRP-таймаута).
5. **Алертинг:** Prometheus, опрашивая `node_exporter` на `gitea-proxy-01` (порт 9100), получает ошибку соединения. Метрика `up{instance="gitea-proxy-01"}` становится равной `0`. Через 1 минуту Alertmanager отправляет уведомление `InstanceDown`.

### Восстановление упавшего узла 

**Контекст:** Узел `gitea-proxy-01` был полностью удален (`docker stop gitea-proxy-01 && docker rm gitea-proxy-01`) из-за фатального сбоя операционной системы. Трафик в данный момент успешно обслуживается через резервный узел `gitea-proxy-02`. Необходимо вернуть кластер к состоянию полной избыточности (High Availability).


**Шаги восстановления:**

1. **Создание чистой среды:** Инженер запускает команду Docker Compose для создания нового контейнера из базового образа (Ubuntu 22.04 + systemd):
```bash
docker-compose up -d gitea-proxy-01

```


2. **Применение конфигурации (GitOps / IaC):** Инженер использует Ansible для приведения "чистого" контейнера в нужное состояние. Благодаря идемпотентности плейбуков, можно запустить настройку только для конкретного узла, не затрагивая остальные:
```bash
ansible-playbook -i inventory.ini deploy.yml -l gitea-proxy-01 --tags haproxy,keepalived,agents

```


3. **Что делает Ansible (Order of Operations):**
* **База:** Устанавливает часовой пояс, обновляет кэш apt.
* **Keepalived:** Устанавливает пакет, генерирует `keepalived.conf` из шаблона (где узел настроен как `MASTER` с приоритетом 110) и запускает службу.
* **HAProxy:** Устанавливает пакет, копирует конфигурацию балансировки (с указанием узлов Gitea) и запускает службу.
* **Observability:** Устанавливает и запускает `node_exporter` и `promtail` для возвращения узла в систему мониторинга.


4. **Возврат трафика (Failback):**
* Как только Keepalived на восстановленном `gitea-proxy-01` запускается, он рассылает VRRP-пакеты со своим изначальным приоритетом (110).
* Узел `gitea-proxy-02` (текущий мастер с приоритетом 100) видит пакеты с более высоким приоритетом и переходит в состояние `BACKUP`.
* VIP-адрес `172.20.0.20` возвращается на `gitea-proxy-01`.


5. **Нормализация состояния:** Prometheus снова видит `up{instance="gitea-proxy-01"} == 1`. Алерт `InstanceDown` разрешается (Resolve). Кластер восстановлен менее чем за 5 минут.

### Сценарий 2: Отказ приложения (Client/App Failure - Gitea)

**Контекст:** Пользователь (или CI/CD runner) обращается к Gitea через браузер или Git-клиент по адресу `http://172.20.0.20:3000`. Этот VIP находится на `gitea-proxy-01`. Прокси маршрутизирует трафик на два backend-сервера: `gitea-node-01` (primary) и `gitea-node-02` (backup)

**Событие:** Служба `gitea.service` на узле `gitea-node-01` внезапно останавливается

**Цепочка событий (Failover):**

1. **HAProxy Health Check Failure:**
* HAProxy на узле `gitea-proxy-01` (и `gitea-proxy-02`) постоянно опрашивает backend-узлы согласно директиве `option httpchk GET /`.
* Как только Gitea на `gitea-node-01` падает, HAProxy перестает получать успешный HTTP-ответ (200 OK) на свои проверочные запросы.
* После нескольких неудачных попыток (определяемых параметрами `fall` и `inter` в конфигурации, обычно несколько секунд), HAProxy помечает бэкенд `gitea-node-01` как `DOWN`.


2. **Перенаправление трафика (Traffic Rerouting):**
* Поскольку основной бэкенд `DOWN`, HAProxy автоматически активирует бэкенд `gitea-node-02`, который был помечен параметром `backup` в `gitea.cfg.j2`.
* Все *новые* входящие HTTP-соединения и Git-операции (push/pull) прозрачно перенаправляются на `gitea-node-02`. Текущие сессии, обрабатываемые упавшим узлом, оборвутся, но при обновлении страницы пользователь попадет на резервный узел.


3. **Алертинг:**
* Prometheus через `node_exporter` (или напрямую через метрики Gitea `/metrics`) фиксирует отсутствие процесса или недоступность порта 3000 на `gitea-node-01`.
* Срабатывает правило в Alertmanager, и команда получает уведомление: `InstanceDown` или `ServiceGiteaDown` (в зависимости от настроенных `alerts.yml.j2`).

**Шаги восстановления:**

1. **Перезапуск сервиса:** Если проблема была кратковременной, достаточно просто перезапустить службу (или это сделает systemd, если настроено `Restart=always` в `gitea.service.j2`):
```bash
systemctl restart gitea
```
*Если проблема серьезнее, может просто перевыполнить Ansible-плейбук для этого узла.*
2. **Failback:** Как только `gitea-node-01` успешно запускается и начинает отвечать 200 OK на проверки `/`, HAProxy помечает его как `UP`.
3. Трафик автоматически возвращается на основной узел `gitea-node-01`, а `gitea-node-02` снова переходит в режим ожидания (`backup`).


### Сценарий 3: Отказ основной базы данных

**Контекст:** Кластер PostgreSQL состоит из двух узлов (`db-node-01` — Primary, `db-node-02` — Standby), работающих в режиме асинхронной потоковой репликации. За мониторинг состояния и failover отвечает демон `repmgrd`. Доступ приложения к базе данных осуществляется через плавающий адрес `db_vip` (управляется `keepalived`), который всегда находится на активном мастере.

**Событие:** Аппаратный или программный сбой на узле `db-node-01` (например, процесс `postgres` убит OOM Killer, или контейнер полностью остановлен).

**Цепочка событий (Auto-Failover):**

1. **Детектирование сбоя (`repmgrd`):**
* Демон `repmgrd` на узле `db-node-02` регулярно опрашивает `db-node-01`.
* При недоступности мастера `repmgrd` выполняет несколько повторных попыток подключения (согласно параметрам `reconnect_attempts` и `reconnect_interval` в `repmgr.conf`).


2. **Продвижение реплики (Promotion):**
* Исчерпав попытки, `repmgrd` на `db-node-02` инициирует процедуру failover. Выполняется команда `repmgr standby promote`.
* `db-node-02` выходит из режима восстановления (recovery) и начинает принимать запросы на запись, становясь новым Primary-узлом.


3. **Миграция VIP (`keepalived`):**
* Одновременно с этим, `keepalived` на `db-node-02` фиксирует отсутствие VRRP-анонсов от `db-node-01` (или отрабатывает локальный health-check).
* `keepalived` переводит `db-node-02` в состояние `MASTER` и забирает IP-адрес `db_vip` на свой сетевой интерфейс, отправляя GARP-пакет для обновления ARP-таблиц в сети.


4. **Возобновление работы приложения:**
* Сервис Gitea на мгновение теряет связь с БД, что приводит к 500 ошибкам для пользователей.
* При следующей попытке соединения трафик через `db_vip` маршрутизируется на новый активный мастер (`db-node-02`). Работоспособность Gitea полностью восстанавливается.


5. **Алертинг:**
* Prometheus фиксирует недоступность таргетов `postgres_exporter` и `node_exporter` на `db-node-01`.
* Alertmanager отправляет SRE-команде критический алерт (например, `PostgresPrimaryDown` или `InstanceDown`).



**Шаги восстановления**

Восстановление упавшего мастера требует ручного вмешательства, чтобы избежать состояния Split-Brain. Строго **не рекомендуется** слепо перезапускать исходный Ansible-плейбук, так как в `inventory.ini` узел `db-node-01` жестко задан как мастер (`is_master=true`), что разрушит текущий рабочий кластер.

1. **Изоляция и запуск старого узла:**
* перезапускаем упавший контейнер: `docker start db-node-01`.
* Убедиться, что старый процесс `postgres` не запустился самостоятельно и не пытается забрать VIP (если `keepalived` стартует раньше, его нужно принудительно перевести в `BACKUP` или настроить `nopreempt`).


2. **Реинтеграция узла (Rejoin):**
* На `db-node-01` необходимо очистить устаревшую директорию данных (или использовать `pg_rewind` для отката расхождений) и перевести узел в статус реплики.
* Выполняется через утилиту `repmgr` от пользователя `postgres`:
```bash
repmgr node rejoin -d 'host=db-node-02 user=repmgr dbname=repmgr' --force-rewind

```




3. **Синхронизация и проверка:**
* Проверить статус кластера:
```bash
repmgr cluster show

```


* Вывод должен показать `db-node-02` как `primary` и `db-node-01` как `standby`.


4. **Возврат ролей (Опционально / Switchover):**
* Если топология требует, чтобы `db-node-01` снова стал мастером, выполняется контролируемый switchover (запускается на текущей реплике `db-node-01`):
```bash
repmgr standby switchover

```


* Во время switchover `repmgr` сам остановит старый мастер, продвинет новый и поменяет их роли местами. VIP автоматически переедет обратно благодаря Keepalived.


### Сценарий 4: Отказ узла сетевого хранилища (Storage Layer Failure - NFS Ganesha)

**Контекст:** Хранилище реализовано на двух узлах (`storage-01`, `storage-02`), которые экспортируют общую директорию (предположительно поверх GlusterFS или распределенного блочного устройства) с помощью NFS-сервера Ganesha в user-space. Доступ к экспорту осуществляется через плавающий IP-адрес `storage_vip` (`172.20.0.30`), управляемый `keepalived`. Узлы приложения Gitea монтируют этот VIP.

**Событие:** Узел `storage-01` (текущий мастер `keepalived`) выходит из строя

**Цепочка событий (Failover):**

1. **Детектирование сбоя (`keepalived`):**
* Процесс `keepalived` на `storage-02` перестает получать VRRP-анонсы от `storage-01` (или отрабатывает `vrrp_script`, если процесс `nfs-ganesha` падает на самом мастере, понижая его приоритет).


2. **Миграция VIP:**
* Узел `storage-02` переходит в состояние `MASTER` и забирает себе IP-адрес `172.20.0.30`, рассылая GARP-запросы.


3. **Поведение клиентов (Gitea Nodes):**
* Клиенты NFS (узлы Gitea) используют опции монтирования `hard,intr` (по умолчанию для NFSv3) или аналогичные. Это означает, что при обрыве соединения I/O-операции процессов Gitea (чтение/запись в репозитории) блокируются (переходят в состояние "D" - Uninterruptible sleep).
* После того как VIP успешно переезжает на `storage-02` и Ganesha на нем готов принимать запросы (NFS grace period), TCP-соединения восстанавливаются.
* I/O-операции "размораживаются", и Gitea продолжает работу без потери данных (при условии, что backend-ФС синхронна). Возможна кратковременная задержка (latency spike) для конечных пользователей, выполняющих `git push/pull` или просматривающих файлы через веб-интерфейс.


4. **Алертинг:**
* Prometheus не может получить метрики с `node_exporter` на `storage-01`.
* Alertmanager отправляет уведомление `InstanceDown` или `StorageNodeDown` для SRE-команды.



**Шаги восстановления (Disaster Recovery / Failback):**

1. **Изоляция и запуск старого узла:**
* Перезапускаем упавший контейнер: `docker start storage-01`.

2. **Реинтеграция в кластер:**
* Так как Ganesha сам по себе stateless (состояние хранит backend-ФС), узел просто нужно вернуть в строй.
* Если контейнер создается с нуля (`docker-compose up -d storage-01`), достаточно прогнать плейбук:
```bash
ansible-playbook -i inventory.ini deploy.yml -l storage-01 --tags storage,keepalived,agents
```


3. **Синхронизация данных:**
* Если GlusterFS требует времени на синхронизацию дельты (split-brain resolving) после даунтайма, необходимо дождаться полного завершения этого процесса *до* возвращения VIP-адреса на `storage-01`.


4. **Failback VIP:**
* Если `keepalived` на `storage-01` настроен с приоритетом выше, чем у `storage-02`, он автоматически заберет VIP обратно сразу после старта. Клиенты NFS снова испытают кратковременную "заморозку" I/O во время NFS grace period на новом сервере.
* Для минимизации прерываний в production часто используют флаг `nopreempt` в `keepalived`, чтобы VIP не перепрыгивал обратно автоматически, а ждал окна обслуживания.

### Сценарий 5: Восстановление БД и Storage из бэкапа

**Контекст:** Произошла потеря данных. Например, администратор случайно выполнил `DROP DATABASE gitea` или удалил все репозитории (`rm -rf /data/brick1/gv0/gitea-repositories`), и эта ошибка мгновенно реплицировалась на резервные узлы (split-brain/failover в данном случае не поможет, так как данные уничтожены логически). Единственный способ вернуть сервис — восстановить состояние из `backup-srv`.

В  инфраструктуре:

* **БД:** бэкапится агентом на `db-node-01` с использованием логического дампа `pg_dumpall`, который стримится напрямую в Restic (файл `dumpall.sql` внутри снепшота).
* **Storage:** бэкапится агентом на `storage-01`, сохраняя всю иерархию файлов из `/data/brick1/gv0`.

#### 1: Подготовка к восстановлению

Перед восстановлением необходимо остановить Gitea, чтобы предотвратить появление новых (рассинхронизированных) данных и разорвать текущие подключения к БД и NFS.

```bash
# На узле управления (Ansible Controller) остановим Gitea
ansible gitea_servers -i inventory.ini -m service -a "name=gitea state=stopped" -b

```

#### Этап 2: Поиск нужного снапшота в  Restic



```bash

# Устанавливаем переменные окружения и смотрим снапшоты
docker exec -it backup-srv bash -c "RESTIC_REPOSITORY=rest:http://backup:SuperSecretRestPassword@localhost:8000/ RESTIC_PASSWORD='ПАРОЛЬ' restic snapshots"



# Пример вывода:
ID        Time                 Host             Tags        Paths
----------------------------------------------------------------------------
424b20a9  2026-05-10 03:00:27  pg-cluster                   /dumpall.sql
4311090d  2026-05-10 03:00:27  storage-cluster              /data/brick1/gv0
...
```

#### Этап 3: Восстановление PostgreSQL

Восстановление БД выполняется на текущем Primary

1. **Извлечение дампа из Restic:**
Выгружаем файл `dumpall.sql` из снапшота бд в временную директорию
```bash
# На db-node-01:
restic restore 4a2b1c3d --target /tmp

```


2. **Очистка поврежденной БД (опционально):**
Так как мы используем `pg_dumpall`, он содержит команды `CREATE DATABASE`. Если база существует, но повреждена, её нужно пересоздать (или использовать флаг `--clean` при дампе, если он был настроен). В нашем случае (исходя из роли `gitea.yml`), проще дропнуть и накатить заново:
```bash
su - postgres -c "psql -c 'DROP DATABASE gitea;'"

```


3. **Импорт дампа:**
```bash
su - postgres -c "psql -f /tmp/dumpall.sql postgres"

```


4. **Синхронизация реплики:**
Так как потоковая репликация (`repmgr`) активна, все восстановленные данные автоматически и практически мгновенно синхронизируются на `db-node-02`. БД восстановлена.

#### Этап 4: Восстановление сетевого хранилища (NFS/GlusterFS)

Восстановление хранилища выполняется на текущем **Master-узле хранилища** (например, `storage-01`).

1. **Извлечение файлов из Restic:**
Мы восстанавливаем файлы непосредственно в точку монтирования/экспорта.
```bash
# На storage-01:
# Заменяем 9f8e7d6c на ID снепшота хранилища
restic restore 9f8e7d6c --target /

```


*Примечание: Restic восстанавливает полные пути, поэтому `--target /` положит файлы обратно в `/data/brick1/gv0/`.*
2. **Проверка прав доступа (Permissions):**
Убедитесь, что восстановленные файлы принадлежат пользователю `git`/`gitea` (в зависимости от настроек uid/gid в NFS экспорте `ganesha.conf.j2`).
```bash
chown -R 1000:1000 /data/brick1/gv0/gitea-repositories

```


3. **Синхронизация Storage Cluster:**
Если под капотом используется GlusterFS (на что намекает путь `/data/brick1/gv0`), запись файлов на один узел (brick) может вызвать рассинхронизацию (split-brain). В идеале, восстановление должно производиться через точку монтирования GlusterFS (клиент), а не напрямую в brick, чтобы система сама реплицировала данные на `storage-02`. Если восстановление шло напрямую в brick, потребуется запустить `gluster volume heal gv0 full`.

#### Этап 5: Финализация и проверка

1. **Запуск Gitea:**
